# Roadmap

Phased path from the current single-app proof of concept ([ARCHITECTURE.md](ARCHITECTURE.md), "Current
architecture") to the target architecture. Phases are ordered by dependency, not necessarily by calendar time.
No new agents are created before Phase 3, per current instructions.

## Phase 0 — Baseline (done)

What already exists and works, for reference:

- End-to-end pipeline proven for one story ([SCRUM-101](user_stories/SCRUM-101-ecommerce-checkout.md)) against
  one app (SauceDemo): planner → generator → healer, executed across chromium/firefox/webkit.
- Custom reporting pipeline: JSON-first results, HTML/PDF/Excel outputs, run archiving via
  [scripts/report-lifecycle.js](scripts/report-lifecycle.js).
- CI runs the generated suite on push/PR ([.github/workflows/playwright.yml](.github/workflows/playwright.yml)).

## Phase 1 — Stabilize what's already mid-flight

The repo currently has an in-progress reporting refactor (deleted manual-exploratory screenshots/summaries,
several new `scripts/report-*.js` files not yet reflected everywhere). Before adding new capability:

- [ ] Reconcile the reporting script set (`generate-report.js`, `generate-test-case-workbook.js`,
      `execution-report-reporter.js`, `report-lifecycle.js`, `report-utils.js`) so there is one clear pipeline
      from raw JSON results to each output format, with no dead scripts left from the previous approach.
- [ ] Confirm `test-results/SCRUM-101-checkout-test-report.md` and `execution-report.html/.pdf` are generated
      from the same underlying data, not maintained independently.
- [ ] Replace the multi-selector fallback arrays in
      [tests/saucedemo-checkout/checkout.spec.js](tests/saucedemo-checkout/checkout.spec.js) with the single
      selector the planner actually resolved, once the plan records it (see Phase 2).

**Exit criteria:** one documented command/flow regenerates all reports from a completed test run, with no
manual steps and no orphaned scripts.

## Phase 2 — Make the pipeline config-driven, not SauceDemo-hardcoded

- [ ] Introduce `config/targets/<name>.json` (base URL, credentials, environment) as an input the orchestrator
      and all three agents read, replacing literal strings like `https://www.saucedemo.com` /
      `standard_user` / `secret_sauce` embedded in spec files.
- [ ] Extend the planner's saved plan format to record the selector/locator it actually used per element
      (an explicit planner → generator data contract), removing the need for fallback selector lists.
- [ ] Introduce a `traceability.json` (or equivalent) generated by the planner mapping acceptance criteria to
      test case IDs, later updated with execution results — replacing convention-only linking (`TC-001`
      matching a heading in one file and a filename in another).

**Exit criteria:** running the pipeline against a second, different target app requires only a new user story
and a new config file — zero edits to agent definitions or shared scripts.

## Phase 3 — Formalize the missing agents

Only after Phases 1–2 land (config and contracts need to exist first, otherwise these agents have nothing
stable to consume). This is the first phase that creates new agents:

- [ ] `qa-documentation` agent: owns generating the Markdown/HTML/PDF/chart deliverables and the coverage/
      traceability report from execution data — currently done by scripts with no agent driving them.
- [ ] `git-ops` agent: owns staging, committing, and pushing generated artifacts with the standard commit
      message template — currently a manual/orchestrator-described step, not a bounded agent.

Both should follow the existing pattern: narrow tool list, single MCP server dependency, one clear
responsibility — matching [playwright-test-planner](.github/agents/playwright-test-planner.agent.md),
[playwright-test-generator](.github/agents/playwright-test-generator.agent.md), and
[playwright-test-healer](.github/agents/playwright-test-healer.agent.md).

**Exit criteria:** Steps 6 and 7 of `Prompt_E2E.md` are executed by named agents with their own `.agent.md`
definitions, the same way steps 2, 4, and 5 already are.

## Phase 4 — Multi-story orchestration

- [ ] Support a backlog of user stories under `user_stories/` rather than a single file, with the orchestrator
      iterating the full pipeline per story into per-story `specs/<story>/`, `tests/<story>/`,
      `reports/<story>/`.
- [ ] Aggregate traceability and coverage across stories, not just within one.

**Exit criteria:** adding a second user story alongside SCRUM-101 produces a second, independent suite and
report set without any manual folder wrangling.

## Phase 5 — Trend and history as first-class data

`report-lifecycle.js` already archives prior runs under `test-results/history/` when `REPORT_HISTORY=true` —
this phase makes that data useful instead of just retained:

- [ ] Flake-rate tracking per test case across historical runs.
- [ ] Healing success rate trend (how often the healer fixes vs. how often it falls back to `test.fixme()`).
- [ ] Execution trend charts wired into the dashboard using real historical data instead of a single run.

**Exit criteria:** the "Healing Success Rate Chart" and "Execution Trend Chart" already named as deliverables in
`Prompt_E2E.md` are populated from real multi-run history, not a single snapshot.

## Phase 6 — Bring the agent loop into CI

Today CI ([.github/workflows/playwright.yml](.github/workflows/playwright.yml)) only runs the already-generated
suite; it never re-plans, re-generates, or heals.

- [ ] Add an optional/scheduled CI job that runs the healer agent against the existing suite when the target
      app changes, opening a PR with fixes instead of just reporting red.
- [ ] Consider a nightly or on-demand job that reruns planning against the live app to detect drift between the
      recorded plan and current UI (new elements, changed flows) and flags it for review.

**Exit criteria:** a UI change in the target app can be detected and partially self-healed by CI without a human
manually invoking the healer agent locally first.

---

**Not planned:** support for non-Playwright frameworks, native mobile testing, load/performance/security
testing, or autonomous (human-out-of-the-loop) release decisions — these remain explicit non-goals per
[PROJECT_VISION.md](PROJECT_VISION.md).
