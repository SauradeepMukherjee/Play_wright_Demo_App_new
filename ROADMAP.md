# Roadmap

Phased path from the current single-app proof of concept ([ARCHITECTURE.md](ARCHITECTURE.md), "Current
architecture") to the target architecture. Phases are ordered by dependency, not necessarily by calendar time.

## Phase 0 — Baseline (done)

What already exists and works, for reference:

- End-to-end 5-agent pipeline proven for one story ([SCRUM-101](user_stories/SCRUM-101-ecommerce-checkout.md))
  against one app (SauceDemo): requirement analysis → test planning → manual test case generation → automation
  generation → healing, executed across chromium/firefox/webkit, orchestrated by
  [`run-qa-pipeline`](.claude/skills/run-qa-pipeline/SKILL.md) with three human approval checkpoints.
- Custom reporting pipeline: JSON-first results, HTML/PDF/Excel outputs, run archiving via
  [scripts/report-lifecycle.js](scripts/report-lifecycle.js).
- Auto git delivery (Conventional Commits, no approval checkpoint) as the pipeline's final step.

**Not yet true, corrected from an earlier version of this roadmap:** there is no CI in this repo. No
`.github/workflows/` directory exists. Phase 6 below now starts from "add CI" rather than "extend existing CI".

## Phase 1 — Stabilize what's already mid-flight

- [ ] Reconcile the reporting script set (`generate-report.js`, `generate-test-case-workbook.js`,
      `execution-report-reporter.js`, `report-lifecycle.js`, `report-utils.js`) so there is one clear pipeline
      from raw JSON results to each output format, with no dead scripts left from previous approaches.
- [ ] Confirm `test-results/SCRUM-101-checkout-test-report.md` and `execution-report.html/.pdf` are generated
      from the same underlying data, not maintained independently.
- [ ] Fix acceptance-criteria coverage mapping: the latest SCRUM-101 report shows 2 of 5 ACs at "0/5 — not
      executed" and 15 automated scenarios with no AC mapping, even though the suite itself is 100% passing.
      The traceability fields exist (Requirement Mapping / Scenario Mapping on generated test cases); the gap
      is in keeping them populated and consistent through planner → generator → report.
- [ ] Replace the multi-selector fallback arrays in
      [tests/saucedemo-checkout/](tests/saucedemo-checkout/) with the single selector the planner actually
      resolved, once the plan records it (see Phase 2).

**Exit criteria:** one documented command/flow regenerates all reports from a completed test run, with no
manual steps, no orphaned scripts, and acceptance-criteria coverage accurately reflects what actually ran.

## Phase 2 — Make the pipeline config-driven, not SauceDemo-hardcoded

- [ ] Introduce `config/targets/<name>.json` (base URL, credentials, environment) as an input the orchestrator
      and all agents read, replacing literal strings like `https://www.saucedemo.com` / `standard_user` /
      `secret_sauce` embedded directly in spec files (confirmed still present in all 5 spec files today).
- [ ] Extend the planner's saved plan format to record the selector/locator it actually used per element
      (an explicit planner → generator data contract), removing the need for fallback selector lists.
- [ ] Introduce a `traceability.json` (or equivalent) generated by the planner mapping acceptance criteria to
      test case IDs, later updated with execution results — replacing convention-only linking (`TC-001`
      matching a heading in one file and a filename in another).

**Exit criteria:** running the pipeline against a second, different target app requires only a new user story
and a new config file — zero edits to agent definitions or shared scripts.

## Phase 3 — Formalize the missing responsibilities (done, via skills not new agents)

Originally planned as two new agents. In practice, both responsibilities are already covered without adding
agent definitions:

- [x] Documentation/reporting: the [`generate-qa-report`](.claude/skills/generate-qa-report/SKILL.md) skill
      owns regenerating the Markdown/HTML/PDF/Excel deliverables from `test-results/raw-results/*.json`.
- [x] Git delivery: step 8 of `run-qa-pipeline` owns staging, committing, and pushing generated artifacts with
      the repo's Conventional Commits convention.

This satisfies the original goal (narrow, single-purpose, no ad-hoc manual steps) via CLAUDE.md's
"One Skill, One Capability" pattern rather than via new subagents — skills were the better fit since neither
step needs live-browser MCP interaction or its own tool-scoped agent identity. No further agent work is planned
for these two responsibilities.

## Phase 4 — Multi-story orchestration

- [ ] Support a backlog of user stories under `user_stories/` rather than a single file, with the orchestrator
      iterating the full pipeline per story into per-story `specs/<target>/<story>/`, `tests/<target>/<story>/`.
      `reports/<story>/` is already scoped this way today (see `reports/SCRUM-101/`) — `specs/` and `tests/`
      are the parts still named after the target app only.
- [ ] Aggregate traceability and coverage across stories, not just within one.

**Exit criteria:** adding a second user story alongside SCRUM-101 produces a second, independent suite and
report set without any manual folder wrangling.

## Phase 5 — Trend and history as first-class data

`report-lifecycle.js` already archives prior runs under `test-results/history/` when `REPORT_HISTORY=true`
(confirmed working — dozens of historical run folders already exist) — this phase makes that data useful
instead of just retained:

- [ ] Flake-rate tracking per test case across historical runs.
- [ ] Healing success rate trend (how often the healer fixes vs. how often it falls back to `test.fixme()`).
- [ ] Execution trend charts wired into the dashboard using real historical data instead of a single run.

**Exit criteria:** a "Healing Success Rate" and "Execution Trend" chart are populated from real multi-run
history, not a single snapshot.

## Phase 6 — Add CI, then bring the agent loop into it

There is no CI in this repo today — no `.github/workflows/` directory exists. This phase starts from zero:

- [ ] Add a basic CI workflow that runs `npm run test:e2e` (or `test:ci`) on push/PR against the already-
      generated suite. This alone is new — nothing currently validates the suite automatically.
- [ ] Once that exists, add an optional/scheduled job that runs the healer agent against the suite when the
      target app changes, opening a PR with fixes instead of just reporting red.
- [ ] Consider a nightly or on-demand job that reruns planning against the live app to detect drift between the
      recorded plan and current UI (new elements, changed flows) and flags it for review.

**Exit criteria:** a UI change in the target app can be detected and partially self-healed by CI without a human
manually invoking the healer agent locally first.

---

**Not planned:** support for non-Playwright frameworks, native mobile testing, load/performance/security
testing, or autonomous (human-out-of-the-loop) release decisions — these remain explicit non-goals per
[PROJECT_VISION.md](PROJECT_VISION.md).
